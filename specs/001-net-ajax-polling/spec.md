# Feature Specification: ASP.NET Core 10 メッセージ配信サンプル（テスト戦略学習用）

**Feature Branch**: `001-net-ajax-polling`  
**Created**: 2025-12-14  
**Status**: Draft  
**Input**: "ASP.NET Core 10 の最小構成アプリを題材に、(1) 統合テスト (WebApplicationFactory)、(2) Playwright E2E、(3) Jest の JS 単体テスト、の棲み分けと実装・運用感を学ぶためのサンプルを作る。サーバーは一定間隔で文字列メッセージを生成してバッファに貯め、クライアントはHTTPストリーミング（NDJSON）またはポーリングで取得して画面に追記描画する。"

## 概要

### 目的（ゴール）

このプロジェクトは、ASP.NET Core 10 アプリケーションにおける3種類のテスト手法（統合テスト、E2Eテスト、JavaScriptユニットテスト）の役割分担と実装パターンを学習するための教材サンプルです。

シンプルなメッセージ配信機能を題材に、各テストレイヤーが「何を検証すべきか」「どう書くべきか」「どう運用すべきか」を体験的に理解することが目的です。

### 非ゴール

- 本番環境での使用を想定した実用的なメッセージング基盤の構築
- 高度なパフォーマンスチューニングやスケーラビリティの実装
- 複数ユーザー・マルチテナント対応
- セキュリティ機能（認証・認可・暗号化など）の実装
- データの永続化やメッセージの保証配信

### 想定ユースケース（学習・実験の観点）

1. **テスト戦略の理解**: 統合テスト、E2Eテスト、JSユニットテストそれぞれが何を担当し、どう補完し合うかを学ぶ
2. **実装パターンの習得**: WebApplicationFactory、Playwright、Jestの基本的な使い方と設定方法を実践的に学ぶ
3. **設計の影響確認**: 通信方式や設定の切り替えがテスタビリティにどう影響するかを体験する
4. **リグレッション検証**: コード変更時に各テストレイヤーで何が検出できるかを確認する

## User Scenarios & Testing *(mandatory)*

### User Story 1 - メッセージのリアルタイム配信と表示 (Priority: P1)

開発者は、サーバーが生成したメッセージがブラウザ画面に順次追加表示されることを確認したい。これはアプリケーションの最も基本的な機能であり、これが動作しなければ学習サンプルとして成立しない。

**Why this priority**: コア機能。これがなければ何も始まらない。

**Independent Test**: ブラウザでページを開き、画面上にメッセージが時系列順に表示されることを目視または自動テストで確認できる。

**Acceptance Scenarios**:

1. **Given** サーバーが起動しメッセージを生成中、**When** ブラウザでページにアクセス、**Then** 画面にメッセージが順次追加表示される
2. **Given** 画面にメッセージが表示されている状態、**When** 新しいメッセージが生成される、**Then** 既存メッセージの下に新しいメッセージが追加される
3. **Given** メッセージが複数バッファリングされている、**When** クライアントが取得する、**Then** バッファ内の全メッセージがまとめて表示される

---

### User Story 2 - 通信方式の切り替え (Priority: P2)

開発者は、HTTPストリーミング（NDJSON）とポーリングの2つの通信方式を設定で切り替えて、それぞれの動作と特性を比較・学習したい。

**Why this priority**: 学習サンプルとしての価値を高める重要機能。異なるアプローチの比較により理解が深まる。

**Independent Test**: 設定ファイルで通信方式を変更し、ブラウザでメッセージが正常に配信されることを確認。各方式で独立したテストが実行可能。

**Acceptance Scenarios**:

1. **Given** 設定が「ストリーミング」、**When** ページにアクセス、**Then** NDJSON形式でメッセージが配信される
2. **Given** 設定が「ポーリング」、**When** ページにアクセス、**Then** 定期的なHTTPリクエストでメッセージが取得される
3. **Given** いずれかの方式で動作中、**When** 設定を変更してアプリを再起動、**Then** 新しい方式でメッセージが配信される

---

### User Story 3 - メッセージ取得間隔の調整 (Priority: P2)

開発者は、クライアント側のメッセージ取得間隔を設定で変更し、バッファリング動作やUI更新頻度の変化を観察したい。

**Why this priority**: 設定の柔軟性と動作の可視性を提供し、実験・学習体験を向上させる。

**Independent Test**: 設定ファイルで取得間隔を変更し、実際の取得タイミングとバッファ動作を確認。

**Acceptance Scenarios**:

1. **Given** 取得間隔が1秒に設定、**When** ページにアクセス、**Then** 約1秒ごとにメッセージが画面に反映される
2. **Given** 取得間隔が5秒に設定、**When** 複数メッセージが生成される、**Then** 5秒ごとにバッファ内メッセージがまとめて配信される
3. **Given** 異なる間隔設定、**When** 複数回テストを実行、**Then** 設定に応じた取得タイミングが観察できる

---

### User Story 4 - 各テストレイヤーの実装と実行 (Priority: P1)

開発者は、統合テスト・E2Eテスト・JSユニットテストそれぞれが正常に実行でき、各レイヤーで適切な検証が行われることを確認したい。

**Why this priority**: 学習サンプルの本質的目的。テストが動作しなければ学習目標が達成できない。

**Independent Test**: 各テストプロジェクトを個別に実行し、テストが成功することを確認。

**Acceptance Scenarios**:

1. **Given** 統合テストプロジェクト、**When** テストを実行、**Then** APIエンドポイントとバッファリング動作が検証される
2. **Given** Playwright E2Eテストプロジェクト、**When** テストを実行、**Then** ブラウザでのメッセージ表示とUI動作が検証される
3. **Given** Jest JSテストプロジェクト、**When** テストを実行、**Then** クライアント側JavaScriptロジックが検証される
4. **Given** いずれかのテスト、**When** コードに不具合を混入、**Then** 該当レイヤーのテストが失敗を検出する

---

### Edge Cases

- サーバー起動直後（メッセージがまだ生成されていない）にクライアントがアクセスした場合、どう振る舞うか？
- メッセージ生成が非常に高速で、バッファが溢れる可能性がある場合、どう制御するか？
- クライアントが長時間接続を維持したまま放置された場合、どう処理するか？
- 不正な設定値（負の数、極端に大きな値）が指定された場合、どうバリデートするか？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: サーバーは一定間隔で文字列メッセージ（タイムスタンプ付き）を生成しなければならない
- **FR-002**: サーバーは生成されたメッセージをメモリ上のバッファ（キュー構造）に保存しなければならない
- **FR-003**: クライアントはWebページを開くことでメッセージ配信を受信できなければならない
- **FR-004**: システムは2種類の通信方式（HTTPストリーミング［NDJSON］とポーリング）をサポートしなければならない
- **FR-005**: 使用する通信方式は設定ファイルで選択可能でなければならない
- **FR-006**: クライアント側のメッセージ取得間隔は設定ファイルで調整可能でなければならない
- **FR-007**: サーバーはクライアントの取得タイミングまでメッセージをバッファリングし、取得時にまとめて配信しなければならない
- **FR-008**: クライアントは受信したメッセージを画面上に時系列順で追加表示しなければならない
- **FR-009**: 統合テストプロジェクトはWebApplicationFactoryを使用してサーバーロジックを検証しなければならない
- **FR-010**: E2EテストプロジェクトはPlaywright（.NET版）を使用してブラウザ動作を検証しなければならない
- **FR-011**: JSテストプロジェクトはJestを使用してクライアント側JavaScriptロジックを検証しなければならない
- **FR-012**: 各テストプロジェクトは最低1つ以上の実装済みテストケースを含まなければならない

### Key Entities

- **メッセージ**: サーバーが生成する配信データ。タイムスタンプ、シーケンス番号、テキスト内容を含む
- **メッセージバッファ**: メモリ上に保持される未配信メッセージのキュー。先入先出で管理される
- **設定情報**: 通信方式（ストリーミング/ポーリング）、取得間隔、メッセージ生成間隔などのパラメータ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ブラウザでページを開いてから10秒以内に最初のメッセージが表示される
- **SC-002**: 設定された取得間隔（1秒、5秒など）に応じて、実際のメッセージ配信タイミングが±10%以内の精度で動作する
- **SC-003**: 通信方式を切り替えても、画面上のメッセージ表示結果が同等である（順序、内容が保証される）
- **SC-004**: 統合テスト、E2Eテスト、JSテストそれぞれが5秒以内に完了する（学習用途として実行速度が重要）
- **SC-005**: 各テストプロジェクトが独立して実行可能であり、相互に依存しない
- **SC-006**: サーバーが100件のメッセージをバッファリングしても、メモリ消費が10MB以下に収まる
- **SC-007**: 開発者が設定ファイルを変更してから、アプリ再起動までの時間が5秒以内で完了する

## 制約・前提条件

### 技術的制約

- データの永続化は行わない（メモリ内で完結）
- 単一サーバー・単一クライアントを想定（複数ユーザー対応不要）
- 認証・認可機能は実装しない
- HTTPS/TLS通信は不要（開発環境でのHTTPで十分）
- メッセージの配信保証や欠損対策は最小限（学習用途のため）

### 環境的前提

- 開発環境: Windows（主） / macOS / Linux（副次）
- .NET 10 SDK がインストール済み
- Node.js / npm がインストール済み（Jestテスト用）
- ブラウザ: Chrome / Edge の最新版（Playwright対象）

### スコープの境界

- リアルタイム性は「準リアルタイム」（数秒の遅延は許容）
- メッセージ内容は学習用のダミーデータで十分（実用的なビジネスロジック不要）
- UIデザインは最小限（CSSスタイリング不要、プレーンHTMLで可）
- エラーハンドリングは基本的なもののみ（詳細なエラー画面不要）

## テスト戦略（範囲定義のみ）

### 統合テスト（WebApplicationFactory）の担当範囲

- サーバー側APIエンドポイントの動作検証（HTTPリクエスト→レスポンス）
- メッセージバッファリングロジックの検証（生成→蓄積→配信）
- 設定ファイルによる動作切り替えの検証
- ストリーミング・ポーリング両方式のサーバー側処理検証

### E2Eテスト（Playwright）の担当範囲

- ブラウザでのページロードとメッセージ表示の検証
- クライアント・サーバー間の統合動作検証（エンドツーエンド）
- UI要素の存在確認とメッセージの画面反映検証
- 通信方式切り替え後の動作確認

### JSユニットテスト（Jest）の担当範囲

- クライアント側JavaScriptロジックの単体検証（DOM操作除く）
- メッセージ受信処理の関数レベルテスト
- データ変換・フォーマット処理のテスト
- モック/スタブを使ったサーバー通信部分の分離テスト

### テスト実行の運用方針

- 各テストは独立して実行可能であること
- CI/CD環境での自動実行を想定
- 開発者がローカルで個別実行できること
- テストの実行速度を重視（フィードバックサイクルの短縮）
